# REST API Specification

Base path: `/api/v1`

## Task endpoints

| Method | Path                | Purpose                      |
| ------ | ------------------- | ---------------------------- |
| GET    | `/tasks`            | List tasks                   |
| GET    | `/tasks/:id`        | Get one task                 |
| POST   | `/tasks`            | Create task                  |
| PUT    | `/tasks/:id`        | Replace editable task fields |
| PATCH  | `/tasks/:id/status` | Change task status           |
| DELETE | `/tasks/:id`        | Delete task                  |
| GET    | `/health`           | Health/readiness check       |
| GET    | `/openapi.json`     | OpenAPI document             |
| GET    | `/docs`             | Swagger UI                   |

`GET /health` is both the health and readiness check. It returns `200` only when the database responds, and `503 SERVICE_UNAVAILABLE` otherwise.

## List query parameters

- `status`: optional status filter
- `search`: optional case-insensitive title substring, matched literally, including `%` and `_`
- `sort`: `dueDate` (the only supported sort, and the default)
- `order`: `asc` (default) or `desc`; tasks without a due date are last in both directions
- `page`: optional, default 1
- `limit`: optional, default 20, maximum 100

Unknown parameters, out-of-range values, and an empty `search` return `400 VALIDATION_ERROR`. Clients omit `search` when there is no term.

## List response

```json
{
  "items": [],
  "page": 1,
  "limit": 20,
  "total": 0,
  "summary": { "all": 0, "pending": 0, "inProgress": 0, "completed": 0 }
}
```

`total` counts tasks matching the current filters. `summary` always counts all tasks, ignoring filters, because the dashboard shows overall totals.

## Create request

```json
{
  "title": "Complete automation framework",
  "description": "Implement API and UI tests",
  "priority": "HIGH",
  "dueDate": "2026-11-15",
  "status": "PENDING"
}
```

## Example response

```json
{
  "id": "generated-id",
  "title": "Complete automation framework",
  "description": "Implement API and UI tests",
  "priority": "HIGH",
  "dueDate": "2026-11-15",
  "status": "PENDING",
  "createdAt": "2026-11-01T09:00:00.000Z",
  "updatedAt": "2026-11-01T09:00:00.000Z"
}
```

IDs and timestamps must be generated by the server. Example values above are illustrative.

`POST` accepts any valid `status`. `priority` defaults to `MEDIUM` and `status` to `PENDING`. Fields such as `id` and timestamps are rejected if sent by a client. Omitted `description` and `dueDate` are returned as `null`.

## Update behavior

- `PUT` requires `title`, `priority`, and `status`. Omitted `description` and `dueDate` are cleared.
- A status change through `PUT` follows the same transition rules as `PATCH`.
- Allowed transitions: `PENDING` to `IN_PROGRESS`, `IN_PROGRESS` to `COMPLETED`, `COMPLETED` to `PENDING`. Anything else, including the same status through `PATCH`, returns `409 INVALID_STATUS_TRANSITION`.
- A past due date is rejected on create. On update, it is accepted only if it is unchanged.
- "Today" is the current calendar date in `APP_TIMEZONE`, which defaults to UTC.
- Concurrent updates are last write wins. There is no version field.

## Error response convention

Use one consistent shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": [
      {
        "field": "title",
        "message": "Title must contain at least 3 characters."
      }
    ],
    "requestId": "correlation-id"
  }
}
```

Do not expose stack traces or internal database details to clients.

## Status codes

- `200`: successful read/update/status change
- `201`: created
- `204`: successfully deleted (no response body)
- `400`: validation failure (`VALIDATION_ERROR`) or malformed JSON (`MALFORMED_JSON`)
- `404`: task or route not found (`NOT_FOUND`)
- `409`: blocked status transition (`INVALID_STATUS_TRANSITION`); never used for duplicate titles
- `413`: request body too large (`PAYLOAD_TOO_LARGE`)
- `500`: unexpected server error (`INTERNAL_ERROR`)
- `503`: health check could not reach the database (`SERVICE_UNAVAILABLE`)

`422` is not used. Every response carries `X-Request-Id`, and error bodies repeat it as `requestId`.

## Test utilities

There are no test reset or seed HTTP routes. Reset and seed are scripts in `apps/api/src/test-support`, excluded from the production build. Before any destructive action, `assertTestDatabase` requires `NODE_ENV=test`, `ENABLE_TEST_UTILITIES=true`, a target file named `test.db`, and a target different from `DATABASE_URL`.

## API coverage expectations

This list applies to internal Supertest integration tests and to external automation in the TaskFlow Automation repository.

Positive CRUD; missing/invalid fields; title/description boundaries; invalid enum values; malformed JSON; unknown IDs; date boundaries; filtering/sorting/pagination; persistence; delete behavior; status rules; concurrent update behavior; database unavailable; server error behavior.
