# REST API Specification

Base path: `/api/v1`

## Task endpoints

| Method | Path                | Purpose                      |
| ------ | ------------------- | ---------------------------- |
| GET    | `/tasks`            | List tasks                   |
| GET    | `/tasks/:id`        | Get one task                 |
| POST   | `/tasks`            | Create task                  |
| PUT    | `/tasks/:id`        | Replace editable task fields |
| PATCH  | `/tasks/:id/status` | Change task status           |
| DELETE | `/tasks/:id`        | Delete task                  |
| GET    | `/health`           | Health/readiness check       |
| GET    | `/openapi.json`     | OpenAPI document             |
| GET    | `/docs`             | Swagger UI                   |

## Suggested list query parameters

- `status`: optional status filter
- `search`: optional title substring
- `sort`: `dueDate` (initial supported sort)
- `order`: `asc` or `desc`
- `page`: optional, default 1
- `limit`: optional, default 20, enforce a reasonable maximum

## Create request

```json
{
  "title": "Complete automation framework",
  "description": "Implement API and UI tests",
  "priority": "HIGH",
  "dueDate": "2026-11-15",
  "status": "PENDING"
}
```

## Example response

```json
{
  "id": "generated-id",
  "title": "Complete automation framework",
  "description": "Implement API and UI tests",
  "priority": "HIGH",
  "dueDate": "2026-11-15",
  "status": "PENDING",
  "createdAt": "2026-11-01T09:00:00.000Z",
  "updatedAt": "2026-11-01T09:00:00.000Z"
}
```

IDs and timestamps must be generated by the server. Example values above are illustrative.

## Error response convention

Use one consistent shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": [
      {
        "field": "title",
        "message": "Title must contain at least 3 characters."
      }
    ],
    "requestId": "correlation-id"
  }
}
```

Do not expose stack traces or internal database details to clients.

## Status codes

- `200`: successful read/update/status change
- `201`: created
- `204`: successfully deleted (no response body)
- `400`: malformed request or invalid query
- `404`: task not found
- `409`: only for genuine state conflicts, not duplicate titles
- `422`: optional convention for semantically invalid fields; choose and document consistently
- `500`: unexpected server error

## Test utilities

The earlier concept included `POST /test/reset` and `GET /test/seed`. These are test-only utilities, not public product endpoints. Before implementing them:

- Require an explicit test environment flag.
- Require a dedicated test database configuration.
- Refuse to start if the configured database is not identified as test.
- Do not register the routes in production builds.
- Prefer invoking seed/reset scripts directly in CI when an HTTP endpoint is unnecessary.

## API test coverage

Positive CRUD; missing/invalid fields; title/description boundaries; invalid enum values; malformed JSON; unknown IDs; date boundaries; filtering/sorting/pagination; persistence; delete behavior; status rules; concurrent update behavior; database unavailable; server error behavior.
